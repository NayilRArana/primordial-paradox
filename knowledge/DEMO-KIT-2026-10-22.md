# Demo kit, 2026-10-22: one command that records the slice, and what it found

Card t_9ebd35dc (DEMO-KIT), testing lane. Written the day the kit landed, so the next worker reads the
method instead of rebuilding it.

## 1. The three files

| File | What it is |
| --- | --- |
| `data/demo/run_001.json` | The input script: 19 events, a 60 step a second clock, the one seed this slice reaches (`title_flash` = `PP_TITLE_FLASH_SEED` = 20261021, `game/scripts/pp_title/pp_title.gml:99`), the game's own log lines as sync points, and the checks the video must pass |
| `tools/play_demo.py` | The player: launches the built game, finds the window by process image name, takes the keyboard focus, plays the script, records with ffmpeg at 60 fps, cuts the frame to a true 3x of the 256x240 screen, then checks the file it wrote |
| `data/demo/manifest.json` | Which of the 32 beat sheet beats the recording covers, with the event that covers each one and the evidence |

`python tools\play_demo.py` is the whole command. `--dry-run` prints the timeline without touching the game,
`--check` re-checks an existing mp4, `--keep-raw` keeps the uncropped window recording.

## 2. Method that worked, in the order it mattered

1. Import `tools/capture_title.py` and use its primitives rather than copying them: `newest_build`,
   `find_window`, `process_image_name`, `ensure_key_focus`, `send_vk_focused`, `ensure_game_visible`,
   `cover_report`, `capture_with_pil`, `find_ffmpeg`, `ffprobe_path`, `probe_duration`. Every one of those was
   already proved on this PC, and each exists because something failed once.
2. Send keys only through the input queue. A posted key is read by the window procedure, not by the game's
   key state, so a scripted run built out of posted keys reads as "the player did nothing".
3. Record the window rectangle, then crop to the viewport that `tools/nes_composite_check.py` finds in a
   pre-roll frame, then scale to 768x720. On this PC the viewport is `[8, 31, 768, 720]` inside a 784x759
   window, so the crop is already 3x and the scale is a no-op. Doing it in that order means the mp4 is the
   game's own pixels and never the desktop's scaling of them.
4. Sync on the game's own log lines (`PP title: intro started`, `starting the run in`) but give every marker
   an absolute fallback step. The log is block buffered when the game's stdout is a file, and this run proved
   it: the second marker arrived at 43.2 s against a 55 s fallback, so the marker worked, but a run that
   trusted it alone would hang the day the buffer behaves differently.
5. Check the finished file, not the intent: ffprobe duration and stream, mean luma per sampled frame,
   distinct colours, palette share, and frame difference. The check is the deliverable, not the print.

## 3. What the check had to learn about compressed frames

The first version of the frame check reused `viewport_box_and_score`, the exact 2C02 palette test the capture
harness uses on a PNG. It failed a correct recording: a real h264 frame of the title measured 18,923 colours
and an exact palette share of 0.000, because chroma is stored at a quarter of the luma resolution and the
quantiser moves every sample a little. The crawl frames, which are almost flat black, still scored 0.966 on
the same test, so the test looked like it worked while it was really measuring how flat the picture was.

The replacement, `palette_share` in `tools/play_demo.py`, asks what share of a frame's pixels sit within 12
levels of a legal 2C02 colour. Measured on the 2026-10-22 recording: title 0.933, menu 0.973, crawl 0.994,
crawl 0.994, and the `rm_pp_ship` room 0.113. A terminal or another window has no 2C02 structure at all, so
the gate still bites, and the allowance is stated in the script rather than hidden in the code.

## 4. The finding this card hands to the audit lane

The `rm_pp_ship` room is drawn off the NES palette. Its three sampled frames carry 11 per cent of pixels
within 12 levels of a legal colour, and the dominant pixels are `rgb(73, 72, 87)` (26.6 per cent),
`rgb(27, 27, 35)` (26.3 per cent) and `rgb(27, 27, 37)` (16.2 per cent), which are greys the 2C02 cannot
output: the nearest legal colours are `(120, 120, 120)` at a distance of 48 and `(0, 0, 0)` at 35.

This is not a capture fault. The frames are the game's own: the run's log carries eight `footstep played`
cues, the room is `rm_pp_ship` (`game/scripts/pp_config/pp_config.gml:170` sets `PP_NEW_GAME_ROOM`), and the
pre-roll viewport test scored 1.000 before the recorder started. It is RULE 0 (palette first) applied to a
room, and it belongs to the audit lane: `knowledge/NES-AUDIT.md:951` already carries the advisory row for
`output/ship_dialogue.png` with 228 findings, and this measurement says the same thing from the recording
side.

The video is still honest as a demo, because the title, the menu and the crawl are on palette and the room is
what exists. It must not be described as palette clean.

## 5. What is not done, and whose it is

- The audio. This host reports no loopback device, so the mp4 carries a rendered stand-in made from
  `assets/audio/title_theme_v5/title_theme_v5.ogg`, labelled in the mp4's own comment metadata and in
  `output/demo/run_001_verify.json`. If Nayil ever installs a loopback capture device, `auto` picks it up and
  the stand-in disappears with no edit.
- The video is 73.5 s of today's slice: beats 1 to 6 covered, beat 7 partial (the 240 step drive), beat 26
  partial (one room, eight steps, one dialogue), and 24 beats unreachable (`data/demo/manifest.json`).
- A second run of the same script is not yet byte identical. The flash stream is seeded and the clock is
  steps, so the two runs land their keys on the same steps; what is not pinned is the attract's own timing
  before the first Enter, which is why the first two presses sit at 10.0 s and 11.5 s and not on a video frame
  boundary. Pinning that needs `PP_TITLE_FLASH_SEED` to also drive the attract wait, which is gamedev's call.
